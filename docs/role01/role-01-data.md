## 操作1：先把明细变成可信的订单，再变成客户快照

1. 校验orders.order_id、customers.customer_id、items的order_id+order_item_id，检查空键和重复。
2. 商品price与freight_value先按order_id分别求和；明细条数单独记录。
3. orders按order_id左连商品汇总，再按customer_id左连客户编号和州。连接校验一对一；输出总行数、唯一键、未匹配及排除量。
4. 未匹配金额保持未知。先按批准时间，再按正商品额筛资格；记录每步分母。
5. 在每个历史窗口按customer_unique_id聚合，并增加snapshot_date。输出键是一人一期，不是单纯一人一行。

**实跑结果：**99441笔订单，112650条商品明细；商品汇总98666笔。连接保留99441行，775笔无商品匹配，客户匹配缺口0。顺序排除160笔无批准时间及629笔金额资格不满足，剩98652笔合格事件。详见[连接及筛选记录](evidence/join-stages.csv)。

## 操作2：用历史计算特征，用未来判断标签

| 项目 | 实施定义 |
|---|---|
| 资格 | 历史窗口至少一笔有批准时间且商品额>0的订单 |
| 历史窗口 | [t−6个自然月,t) |
| 未来窗口 | [t,t+90天) |
| y=1 | 未来至少一笔同口径事件 |
| y=0 | 满足工作观察假设且未来没有事件；不用于填补观察缺口 |
| 暂定观察范围 | [2017-01-01,2018-09-01)，完整性独立证据仍待核 |
| 成熟时点 | t+90天；暂假设无额外入库延迟 |

11项输入：R、F、M、average_order_value、max_order_value、average_item_rows、freight_share、observed_history_days、recent30_orders、recent30_spend、state。金额不包含运费；观察历史长度不是注册年龄。ID、snapshot_date、split、data_version均是元数据，不作为模型输入。

输出各期起止、每日/月记录数、筛选前后客户、正例和复购率。2018-04-01明确标记已见探索，不是未触碰最终测试。三期细节见[覆盖人数表](evidence/coverage-and-cohorts.csv)。

## 操作3：不仅查代码能不能运行，还查是否算对

- 用人工六个边界事件检查历史起点、快照和标签终点的开闭区间。
- 用真实批准订单验证：恰在快照时刻属于未来；快照后移一秒，该事件转入历史。
- 多单客户实例从原始明细复算F、M和运费。公开说明保留金额示例，不公开真实客户编号。
- 三期共15个随机/多单/正例案例追溯；另从原始三表独立复算全部88341条快照的11项特征与y。
- 改变未来事件不改变历史特征；工作范围不足的测试日期被拒绝，不能补造0标签。
- 检查快照后送达和评价记录：最终状态、送达结果、评分没有进入初版特征。商品金额、运费和州的历史可用性仍依赖静态导出假设。
- 特征与标签分文件；所有开放日期属于已见探索期。新最终日期未定，最终标签未生成，不能宣称已封存。
