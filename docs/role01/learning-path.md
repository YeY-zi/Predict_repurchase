# 我的学习路径：从拿到九张表，到交出统一客户快照

[返回导航](README.md) · [岗位实施](role-01-data.md)

## 1 起点：我想用课堂知识，但还没有理解项目

我刚学完Week 10，最初想练习time_series教程、天气数据及深度学习知识，也考虑另找项目。已有Olist小组代码虽然运行过并放到GitHub，但我还不能解释每一步。于是学习目标调整为：从拿到数据开始，自己理解数据结构、提出问题、构建样本和评价设计。

复购快照预测主要是客户层级的二分类与排序任务，不因为使用日期就必须用LSTM。课堂关于历史输入、未来目标、时间先后和信息泄漏的思想可以迁移；采用什么模型要等任务与样本明确后再决定。

## 2 选择岗位：为什么1号不只是“清洗数据”

我比较过EDA、数据与样本、组内反馈等岗位，最终承担1号。实际工作是让不同组员使用同一批客户、同一个快照和同一套标签，能够追溯数据如何形成。一个连接错误或时间口径变化，会传递到分类、分群和汇报数字。

## 3 第一轮困惑：为什么不能直接开始建模？

我曾提出“从头到尾带着我跑一次”的要求，因为预先给定90天、6个月和合格订单，让我不知道这些规则从哪里来。后来把问题分开：

| 层次 | 要回答的问题 | 不能混淆的事情 |
|---|---|---|
| 数据事实 | 有哪些表、字段、时间和记录 | 数据本身不自动规定预测期限 |
| 业务定义 | 服务谁，做什么决策，多久评价 | 90天是工作场景选择，不是数据自动算出的最优值 |
| 实现规则 | 采用哪个事件时刻、哪些订单合格 | 规则要写出，并检查影响 |
| 评价设计 | 哪些时点训练、验证、最终评价 | 不能看完结果再挑最好看的测试期 |

## 4 理解九张表：先问“一行是什么”

| 表 | 一行或键的理解 | 连接时的关键限制 |
|---|---|---|
| orders | 一行一订单，order_id | 本轮订单事实表的主表 |
| customers | customer_id唯一；customer_unique_id可重复 | 前者用于订单侧连接，后者跨订单识别买家 |
| order_items | order_id + order_item_id联合定位明细 | 一笔订单可以多行，不能把明细行数当订单数 |
| payments | 一单可有多条支付记录 | 先按订单确定支付汇总规则 |
| reviews | 一单可能多评 | 评分聚合和选评需要明确规则 |
| products | product_id定位商品属性 | 可给商品明细增加品类等属性 |
| sellers | seller_id定位卖家 | 一单可能涉及多个卖家 |
| translation | 品类原名对应英文名 | 按品类名称匹配并核查唯一性与缺口 |
| geolocation | 邮编前缀不唯一 | 不能直接按邮编把所有坐标拼进客户和卖家 |

我曾问能否按1NF、2NF、3NF理解关系。关系键与函数依赖有助于理解数据，但这次分析重点是确认实际粒度、唯一性和一对多关系；不能因为画出关系图，就默认所有键与外键都有效。

## 5 真正理解金额为什么会重复

假设某订单有3条商品、2条支付，直接通过order_id连接会变成6行。每条商品出现两次，每条支付出现三次。连接语法没有报错，求和却已错误。

正确方法取决于最终统计单位。本轮要“一行一订单”，所以商品金额和运费先按order_id汇总，再接订单、客户。若分析单位本来是商品明细，可以保留明细，但不能在这个层级随意求订单金额总和。

```text
items --按order_id汇总--> 一行一订单的商品额与运费
                                      |
orders --order_id左连接----------------+
   |
   +--customer_id连接customers--> 订单带匿名买家编号
   |
   +--按customer_unique_id与快照聚合--> 一人一期一行
```

完整九表的可选扩展：translation按品类名接products；products按product_id接items；邮编坐标先聚合成一邮编一行，再分别按客户/卖家邮编接customers和sellers；sellers按seller_id接items。支付、评价必须各自形成订单粒度后再接订单。**了解九表关系不等于本轮必须使用九表**；H02初版主要使用orders、customers、items，评价表只参与时点风险检查。

## 6 质量检查不是“缺失就填零、重复就删除”

我依次追问连接缺口、状态、时间、交付延迟、金额和评价：

- 缺失值检查：字段本身缺什么；连接缺口检查：关联键在另一张表找不到什么。两者需要分别记录。
- 没有商品明细：金额未知，不等于商品额0；先保留再按资格规则排除。
- 地理完整重复行与同邮编多坐标不是同一种问题。去重后邮编仍可能不唯一；代表坐标是区域近似位置，不是客户精确地址。
- delivered是导出时看到的最终状态，不能当成下单时已知输入。
- 预计某日送达与实际当天15点送达：按日历日可能不迟，直接比午夜时间戳却可能被算迟；必须先定义标签。
- 商品额、运费、支付额与平台营收不是同一个量；没有成本不能随意算利润。
- 没有评价正文不代表不满意；没有第二单不代表永久流失。

## 7 从“为什么90天”学会区分任务选择与模型评价

我比较过30、60、90、120、180天的含义。固定同一历史名单，延长未来观察窗通常会增加复购人数，**不是模型变得更准确**，甚至还没有开始训练模型。

合理顺序是：业务用途 → 候选期限 → 后续覆盖 → 固定名单比较事件信息 → 换时点检查 → 权衡业务时效与可用验证空间 → 暂定期限并记录理由。

当前沿用团队的六个月历史、90天标签。合格事件定义为批准时间存在且订单商品金额为正，不筛最终送达状态。标签为未来窗口是否出现同口径事件；它描述观察内的复购，不证明联系这些客户能增加复购。营销增量需要另外的对照实验。

## 8 学会处理Notebook和运行环境

我遇到过orders未定义导致后续order_customer、buyer_orders连续报错。这提示Notebook有执行顺序和内存依赖，不能只运行中间一格。

也曾在用户主目录运行项目命令，导致找不到requirements.txt和scripts；需要先进入项目根目录。依赖安装报错与九个CSV解压成功是两件事，不能互相替代。

后来发现Notebook内核仍是Python3.14，而项目依赖装在Python3.12环境。切换到正确内核后显示Python3.12.5、pandas2.3.3。目录检查成功时不必硬改为本机绝对路径；应检查实际工作目录和数据来源。

## 10 当前能解释什么，还有什么要继续学

“已讨论过、代码已跑通”不自动等于本人已经熟练掌握。下面是我的自查目标，而不是已通过的考试记录：

| 自查 | 下一步练习 |
|---|---|
| 能否解释主键、复合键和粒度 | 手算3条商品×2条支付为何变6行 |
| 能否从订单追溯R/F/M | 自己选一名多单客户，复算金额及时间差 |
| 能否区分历史与标签 | 判断起点、终点、恰好快照时刻的订单归属 |
| 能否识别泄漏和覆盖不足 | 解释为何不能把未来评分输入模型、不能用0补缺观察窗 |
| 能否说明交接完成度 | 区分程序通过、已发送、收到、已验收和正式日期核定 |

后续学习：与3号理解时间验证、训练集拟合预处理、最近购买基线和前10%名单指标；理解AP及稀少正例的波动；与4、5号理解聚类和分组错误分析；最后连接回业务解释。尚未声称本轮已完成这些模型工作。
